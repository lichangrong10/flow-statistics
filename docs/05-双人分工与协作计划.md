# 双人前端分工与协作计划（v0.1）

> 说明：文中 Mock 相关分工为历史计划；Mock 层已移除，当前由两人共同负责真实接口联调与页面迭代。


> 前提：**只做前端**；接口先用 Mock（MSW 按 `docs/03-接口契约.md` 实现）；前端 2 人。
> 基线：`docs/04-页面与组件清单.md` 的 38 人天 + Mock 服务 2 人天 = **40 人天**，两人并行约 **5 周**（每周 5 天、每人 20 人天，留 5 天缓冲给评审、设计还原、返工）。

---

## 一、先回答：「一人管理端、一人用户端」行不行

**不建议**，三个硬理由：

| 维度 | 管理端 | 用户端 | 结论 |
|---|---|---|---|
| 工作量 | **6 人天**（用户 1.2 + 厂商 1.4 + 模拟参数 2 + 字典 1 + 日志 0.8） | **29 人天**（其余全部） | 约 1 : 5，第二周就有人空转 |
| 依赖方向 | 复用用户端的 `DataTable`/`StatusTag`/`VendorSelect`/字典/厂商/计划数据 | 不依赖管理端 | 管理端做完了也跑不起来，得等用户端 |
| 耦合 | 模拟参数直接读写分日/维度数据；日志覆盖全站写操作 | 产生这些数据 | 拆「端」不等于拆「模块」，联调时两边都要懂全貌 |

**能成立的前提**：管理端是独立门户（独立登录、独立菜单、独立数据模型）——本项目不是。

**另一种常见分法也不推荐**：一人做「页面」一人做「组件+联调」。组件是页面的一部分，做完就等人；而且两人都在改同一批文件。

## 二、推荐分工：公共层 → 按业务域纵向切

### 2.1 总量与平衡

| 负责人 | 负责域 | 人天 | 说明 |
|---|---|---|---|
| **A** | 基础设施 + 计划域 | **21** | 脚手架、请求层、路由、布局、主题、权限、字典、格式化；投放列表、发布向导、投放详情、报表中心；管理页「厂商 + 字典」页签 |
| **B** | Mock + 数据域 | **19** | MSW 契约服务与演示数据；登录、工作台、数据看板、数据回收；管理页「用户 + 模拟参数 + 日志」页签 |
| 共同 | 联调与测试 | 5（2.5 + 2.5） | 各自页面的接口替换 + 交叉冒烟 |

> 21 vs 19，差 2 人天：A 的「向导」是单点最大风险（5 人天），B 的「数据回收」是第二风险（5 人天），两人各守一个大块，互相 backup 时也说得清。

### 2.2 模块归属明细

| 模块 | 人天 | 归属 | 交付周 |
|---|---|---|---|
| 脚手架 / 请求层 / 路由守卫 / 布局 / 设计令牌 / 权限指令 / 字典 store / 格式化工具 | 3 | A | W1 |
| MSW Mock 服务（51 接口 + 演示数据 + 生成算法） | 2 | B | W1 |
| 登录 | 1 | B | W2 |
| 工作台（6 卡 + 2 图 + 待办） | 2 | B | W2 |
| 投放计划列表（筛选/URL/批量/行操作） | 3 | A | W2 |
| 发布投流向导（4 步 + 校验 + 草稿） | 5 | A | W2–W3 |
| 投放详情（5 页签 + 单日调节） | 3 | A | W3 |
| 数据回收（录入/导入/同步记录） | 5 | B | W3 |
| 数据看板（6 图 + 筛选联动） | 3 | B | W4 |
| 报表中心（异步导出） | 2 | A | W4 |
| 管理页框架 + 厂商 + 字典 | 2.5 | A | W4 |
| 管理页 用户 + 模拟参数 + 日志 | 3.5 | B | W4 |
| 联调、Playwright、截图、性能自测 | 5 | A2.5 / B2.5 | W4–W5 |

### 2.3 为什么这样切

- **依赖最短**：A 先把公共层立起来，B 的 Mock 同步铺开，第二周两人同时进页面，不互相等。
- **域内闭环**：A 的「列表 → 向导 → 详情」是一条完整业务链路，自己就能联调通；B 的「回收 → 看板 → 报表数据源」是另一条数据链路，也自洽。
- **管理页不整端给人**：按页签拆文件（`admin/tabs/*.vue`），A 管框架 + 厂商 + 字典，B 管用户 + 模拟参数 + 日志，工作量补齐且互不碰文件。
- **能力互补**：A 兼设计还原与组件规范（方案 13.3 要求），B 主攻图表与数据生成，联调时两人都能独立定位问题。

## 三、文件所有权（避免合并冲突的硬规则）

| 路径 | 所有者 | 说明 |
|---|---|---|
| `src/api/**` `src/router/**` `src/layouts/**` `src/styles/**`（`chart-theme.ts` 除外） `src/utils/**` `src/constants/**` `src/types/**` `src/directives/**` `src/stores/{user,dict,app,campaign}.ts` | **A** | 基础层只由 A 改；B 需要时提 PR 说明 |
| `src/mocks/**` `src/stores/dashboard.ts` `src/styles/chart-theme.ts` | **B** | Mock 是单一数据源，只由 B 维护 |
| `src/components/{DataTable,StatusTag,AmountText,EmptyState,FilterBar,PageHeader,VendorSelect,VendorTags}.vue` | **A** | 首个使用页面在 A 域 |
| `src/components/{BaseChart,KpiCard,DimensionTabs,ImportDialog,DimensionEditor,AuditLogList}.vue` | **B** | 首个使用页面在 B 域 |
| `src/views/campaign/**` `src/views/report/**` `src/views/admin/index.vue` `src/views/admin/tabs/{VendorTab,DictTab}.vue` | **A** | — |
| `src/views/{login,dashboard,board,stats}/**` `src/views/admin/tabs/{UserTab,MockTab,LogTab}.vue` | **B** | — |

**三条补充规则**
1. `src/types/**` 由 A 维护；B 可 **append-only** 追加新类型，不得修改既有定义（新增接口 DTO 例外需 @A 评审）。
2. 组件「首个使用页面归属」：谁先用到谁写，写完立即补 props 文档到 `04-页面与组件清单.md` §4，另一人只消费不重构（要改接口先提 issue）。
3. 跨域改动（如给 `DataTable` 加虚拟滚动）由所有者实现，另一方只提需求。

## 五、Mock 先行策略（两人如何不打架）

1. **单一数据源**：`src/mocks/db.ts` 只由 B 维护，含演示项目「2026 年太仓分公司全域融数」+ 3 条计划（含 7 种状态样例）+ 分日/维度数据；A 只消费 `api/` 层，不碰 `mocks/`。
2. **按需交付顺序**（B 优先做 A 急用的）：
   - W1：`auth` / `projects` / `campaigns`（列表 + 创建 + 状态动作）
   - W2：`dashboard` / `vendors` / `dicts`
   - W3：`stats`（含 import、dimensions）/ `sync-tasks`
   - W4：`reports` / `users` / `logs` / `mock-profile`
3. **生成算法对齐后端**：`mulberry32` 固定种子、±15% 波动、最大余数法拆分维度、覆盖写——B 在 `src/mocks/generator.ts` 实现一份，切真实接口时不改页面、数值可复现。
4. **契约变更**：任何接口字段改动先改 `docs/03-接口契约.md`，再改 `mocks` + `api`，两人共同确认；不改契约直接改 JSON 视为缺陷。

## 六、协作机制

| 项 | 约定 |
|---|---|
| 分支 | `main` + `feat/<域>-<模块>`（如 `feat/campaign-wizard`）；禁止直推 main |
| PR | ≤400 行净变更；另一方 review 后合并；基础层改动必须 @对方确认 |
| 提交 | 约定式提交（feat/fix/refactor/docs/chore） |
| 每日 | 10 分钟站会：昨天完成 / 今天计划 / 被谁阻塞；阻塞当天在群里说，不隔夜 |
| 质量门 | `pnpm lint` + `pnpm type-check` + `pnpm test` 必须绿才可合并；husky + lint-staged 自动跑 |
| 组件文档 | 组件 props 变更当天更新 `04-页面与组件清单.md` §4 |
| 命名 | 页面组件 PascalCase，文件 kebab-case，页面目录按路由 |

**测试分工**
- Vitest：A 写 `format`/`validate`/`stores`；B 写 `import-parser`/`generator`/图表 option。
- Playwright 5 条主链路：A 登录、发布、导出；B 录入、导入。
- 若按方案配 1 名测试：Playwright 脚本由测试维护，前端只补 `data-testid` 与页面操作路径说明。

**验收分工**

| 截图 | 责任人 | 视频段落 |
|---|---|---|
| 1 工作台 / 5 看板 / 6 报表 / 8 管理-模拟参数 | B | 0:00–0:40 工作台、3:00–5:00 回收+模拟、5:00–6:30 看板 |
| 2 列表 / 3 向导 / 4 详情 / 7 管理-厂商 | A | 0:40–2:00 发布四步、2:00–3:00 审核发布、6:30–7:30 报表 |

## 八、备选方案

- **若增至 3 人**：A 保持基础设施 + 计划域；B 保留 Mock + 数据域；C 接「管理页 + 报表 + 联调测试」，可把周期压到 4 周。
- **若只剩 1 人**：按 `04` §8 的 10 个批次串行，预计 8 周；优先保证「列表 → 向导 → 详情 → 回收 → 看板 → 报表」六页，管理页后置。
- **若坚持按端分**：只能变形为「A = 用户端主链路（29 人天）+ B = 管理端 + 看板 + 报表 + 测试（11 人天）+ B 反向承接回收或详情」。本质仍是域切分，不如直接按本文方案。
